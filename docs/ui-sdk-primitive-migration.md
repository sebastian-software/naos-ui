# Primitive migration matrix: Zag to UI SDK

Planning snapshot: Naos 1.1.0 and `@ui-sdk/core` / `@ui-sdk/web` 0.1.0-beta.14, as inspected in `experiments/ui-sdk` and SDK source. The target is UI SDK, with Zag retiring after its last consumer migrates; plain native controls can remain. The lab’s recommendation to retain Zag is historical assessment, not the current direction. Migrate incrementally, using existing implementations as the behavioral oracle until each family passes its gates.

## Contract and integration rules

- Preserve every exported Naos tag, subpath, generated declaration and manifest entry; attributes/properties, defaults, slots, parts, CSS hooks, event names, detail, bubbling/composition and ordering are defined by the current sources and consumer tests. Treat intentional changes as explicit release decisions, not incidental SDK differences.
- For form-associated components, preserve the form participation, validity, disabled behavior, reset, restoration and submission actually provided by each current component; trace each contract before porting it. The lab found both implementations lose form value after a fieldset is disabled and re-enabled: record and fix separately, with an explicit behavior decision, rather than treating this as proof of correctness.
- The primitive build records `usesDeclarativeShadowDom: false` for every primitive. The runtime/compiler have DSD support elsewhere, but that does not establish a primitive hydration contract. Test pre-upgrade and reconnect behavior for the pilot; investigate DSD separately before treating it as a supported primitive feature or introducing it.
- Naos owns custom-element lifecycle and public surface; an SDK component or core behavior owns each interaction, never two competing layer managers. Mount once per connection, synchronize changing props and slotted children, dispose observers/listeners/timers once on disconnect, and restore a functional instance on reconnect. `internal/zag/service.ts` currently stops state/root effects and bindable cleanup; match externally observable cleanup, not its implementation.
- Public SDK component entry points are `@ui-sdk/core/<name>` for behaviors and `@ui-sdk/web/<name>` for registering the SDK's own custom elements. Web entries are side-effectful, supply their own tag/part composition, and need translation within Naos; they are not drop-in Naos tags. Use only published exports, pin compatible core/web versions, check registration collisions, and avoid undocumented internal paths. Core's `renderer`, `testing`, `date`, `number`, `async-options`, and page-level `overlays`/`shortcuts` are utilities or infrastructure, not component equivalents.
- Lab evidence: SDK popover passed five non-modal Chromium/WebKit cases; modal, full API, styling and DSD were not assessed. The hybrid dismissal layer failed settled Escape because Zag cancels it; do not combine managers. SDK select covered a narrow plain-label form slice, omitting style hooks and open events. The shadow-root splitter missed mouse drag due to document-level retargeting; a composed-path diagnostic fixed that probe only. Firefox could not launch; touch, closed roots and assistive technology remain unverified. Standalone popover 31,251 vs 52,113 gzip bytes; select 33,255 vs 67,870; joint pair 44,574 vs 73,267. Measurements are lab builds, not portfolio budgets.

## Matrix

SDK paths below mean both `@ui-sdk/core/<path>` and, where listed, `@ui-sdk/web/<path>`. An available name is a candidate, not a proven equivalent. The rows cover all 44 components distributed by `packages/primitives/scripts/build-primitives.mjs`. Row test prompts are investigation targets; confirm each against its current source and callers before calling it an existing contract. New behavior needs a separate decision.

Native HTML controls (`button`, `input`, `progress`, labels and form elements) remain valid implementation building blocks. They are not SDK components and must still pass the Naos public contract. Item elements are public components even where they only provide data to a parent. Internal `behavior/*`, `internal/zag/*`, `scope`, `props`, and the machine service are noncomponent implementation APIs; delete only after tracing all consumers and retaining needed presence/context behavior.

## Order and gates

1. Capture current package exports, generated declarations/manifest and representative consumer fixtures; record baseline tests, package sizes and the supported browser matrix. Establish automated black-box comparisons against existing components, including dynamic property/slot mutation and reconnect. No weakening of existing tests.
2. Prove a vertical slice: popover with the complete Naos contract, including current nested-overlay behavior, focus, cleanup and styles; assess DSD separately; then select with rich items and native form boundary. Resolve SDK ownership and any shadow retargeting issues before expanding. Treat the lab as evidence, not production code.
3. Migrate low-coupling families (avatar, progress, button/field, disclosure and tabs), then form controls and collections, then overlays, date/file and remaining custom families. Each batch ships only after its own parity checks and downstream builds. Keep unsupported equivalents on their existing implementation until a deliberate adapter is proven.
4. Run primitive build/type checks and existing suite, consumer tests, browser interaction and accessibility checks on supported engines. Include keyboard, pointer/touch, focus, accessible name/state, disabled/invalid, reset/submission and connect-disconnect-reconnect as relevant; use actual browsers for shadow DOM, forms and DSD. Check no test count silently shrank. Measure representative standalone and shared bundles; compare with recorded baseline and require an explicit size tradeoff decision.
5. Remove Zag helpers and package dependencies only after dependency tracing confirms no remaining users, then rerun full workspace checks, browser matrix, package build/export checks and size measurements. Review release compatibility and retain a rollback path per batch.

## Terra: first implementation slice

Own the popover parity slice in `packages/primitives/src/popover.wc.tsx`, its CSS only where required, a narrowly scoped SDK integration helper if needed, and focused primitive/browser tests; coordinate package/build changes with the integrator. First derive a contract checklist from the existing component, helper, tests and callers. Implement a single SDK-owned interaction behind the same Naos API; do not use the known-failing hybrid layer. Derive supported modes from the current API, then test nested Escape/outside press, focus return, slotted trigger/content, changing attributes, presence, removal while open/reconnect and pre-upgrade behavior. Assess DSD as a separate proposed capability, not established parity. Compare event payload/count/order and styles with baseline in Chromium, WebKit and Firefox where available. Report any unsupported contract, precise failing case, bundle delta and decision needed; do not silently narrow behavior or declare parity on the five-case lab alone. Select is the next slice after this gate and should include fieldset reset/disable coverage.
